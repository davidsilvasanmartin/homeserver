## What this project is

`homeserver` will be a Go CLI (`homeserverctl`) that stands up and tears down a
Kubernetes-based homelab with a single command, on a single Debian production box and
on a local macOS dev cluster, from the same manifests and the same CLI invocations. It
is a from-scratch Kubernetes rewrite of an existing Docker Compose project,
`../auto-homelab`, which is referenced throughout the docs as prior
art for CLI shape, the secrets-strategy pattern, and backup design — but nothing is
ported directly; auto-homelab is a design reference, not a dependency.

## Locked decisions (do not re-litigate)

| Area | Decision |
|---|---|
| Prod hardware | Single Debian 13 box (192.168.1.250), also used as a normal GNOME desktop |
| Prod k8s | `kubeadm`, single node, control-plane taint removed |
| CNI | Cilium, standard mode (kube-proxy kept, not eBPF replacement mode — that's a later follow-up) |
| Ingress | Istio ingress gateway, bound to host ports 80/443 directly (no MetalLB/LoadBalancer) |
| Service mesh | Istio sidecar injection enabled on the apps namespace; mTLS between services via `PeerAuthentication` (`STRICT`) |
| TLS | cert-manager + Cloudflare DNS-01 ACME |
| Secrets | Phase 1: plain Kubernetes `Secret`s generated by the CLI. Phase 2 (deferred): HashiCorp Vault in-cluster + External Secrets Operator. Do not build Vault before Phase 1 works end-to-end. |
| Local dev cluster | `kind` (not k3d/minikube) — closest to vanilla upstream k8s |
| Manifest management | Direct `client-go` apply from the Go CLI; no GitOps controller (no Argo CD/Flux) |
| Config layering | Kustomize (`manifests/base/` + `manifests/overlays/{dev,prod}/`) for first-party manifests; Helm (via its Go SDK) for third-party charts (Istio, cert-manager, Vault, Cilium, ESO) |
| DNS | `*.homeserver.example.com` is internal-only (split-horizon, resolves to 192.168.1.250); other `example.com` subdomains are public via Cloudflare |
| Backups | restic → Backblaze B2, run from in-cluster CronJobs directly against PVCs (no local staging copy) |
| CLI-to-k8s transport | `client-go` only — never shell out to `kubectl` or `docker` |

## Key architectural through-line

Both secrets phases and both cluster environments (dev/prod) are designed to converge
on the same end state so that switching between them is additive, not a rewrite:

- Secrets: Phase 1 (`Secret`s written directly by the CLI) and Phase 2 (Vault + ESO)
  both terminate in an ordinary Kubernetes `Secret` object consumed via
  `secretKeyRef`/`envFrom` — service manifests never change between phases.
- Environments: dev (`kind`, Mac) and prod (`kubeadm`, Debian) run the *same* manifests
  and the *same* CLI commands; only `--env` and the credentials/cluster context differ.

When extending either the secrets model or a service definition, preserve this
convergence — e.g. a new service's manifest should reference secrets by name only, and
never assume which phase or environment it's running under.
