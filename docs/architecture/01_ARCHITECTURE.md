# Architecture

This document describes the system-level design of the homeserver: the cluster,
networking, secrets, storage, and backup model. It assumes no prior Kubernetes
knowledge — concepts are introduced inline in **📘 boxes** the first time they're
used. For the Go CLI that operates this system, see [DESIGN.md](02_DESIGN.md).

This design draws heavily on `../../../auto-homelab`, an existing
Docker Compose-based homelab that already runs Traefik + Cloudflare TLS +
restic/Backblaze backups successfully, and on that project's own (never
implemented) Kubernetes migration research in
`documentation/kubernetes-migration/`. We're building fresh, not porting code,
but reusing the parts of that design that already proved out.

## Decisions locked in so far

| Area | Decision |
|---|---|
| Prod hardware | Single Debian 13 box (192.168.1.250), used as a normal desktop too (GNOME, monitor attached) |
| Prod k8s | `kubeadm`, single node, control-plane node also runs workloads |
| CNI | Cilium, standard mode (kube-proxy kept in place — see below) |
| Ingress | Istio ingress gateway |
| Service mesh | Istio sidecar injection enabled on `homeserver-apps`; mTLS between services via `PeerAuthentication` |
| TLS | cert-manager + Cloudflare DNS-01 |
| Secrets | Phase 1: plain Kubernetes `Secret`s, generated by the CLI. Phase 2 (later): migrate to HashiCorp Vault in-cluster |
| Backups | restic → Backblaze B2 (same tool as today) |
| Local dev | Same CLI, same manifests, different cluster (Mac) and different (test) credentials |
| Manifest management | Direct `kubectl apply`-style from the Go CLI, no GitOps controller |

## 1. Cluster topology

📘 **Kubernetes concept — Node, control plane, kubeadm:** A Kubernetes *cluster*
is one or more *Nodes* (machines) managed by a *control plane* (the API server,
scheduler, etc.) that decides what runs where. `kubeadm` is the standard tool
for bootstrapping a self-managed cluster on any Linux box — it's what you use
when you're not on a managed cloud (EKS/GKE/AKS). Normally the control-plane
node is *tainted* so regular workloads can't be scheduled on it (to protect
cluster-critical processes); on a single-node homelab we remove that taint so
the one node can run everything.

- Debian 13 + `containerd` as the container runtime (kubeadm's default,
  replaces the Docker daemon the old project used directly).
- One node, control-plane taint removed.
- Cilium as the CNI (Container Network Interface — the plugin responsible for
  pod-to-pod networking and `NetworkPolicy` enforcement). Per your steer
  towards the "industry standard" without piling on every new concept at once,
  we run Cilium in its standard mode, **alongside `kube-proxy`**, not in its
  full eBPF kube-proxy-replacement mode. That upgrade is a clean, isolated
  follow-up once the basics are comfortable.

📘 **Namespace:** a Namespace is a logical partition inside one cluster — a way
to group and isolate related objects (and apply different access/network
policy per group) without needing separate clusters. Two namespaces:

- `homeserver-system` — `istiod` (Istio's control plane) + the Istio ingress
  gateway, cert-manager, Vault, External Secrets Operator, backup
  infrastructure.
- `homeserver-apps` — Immich, Calibre, Paperless, Firefly, Navidrome, etc. Has
  the `istio-injection=enabled` label, so every Pod here gets an Envoy sidecar
  (see below).

## 2. Networking & Ingress

📘 **Service, Ingress:** Pods are ephemeral and get new internal IPs whenever
they restart. A `Service` gives a stable internal name/IP in front of a set of
Pods. An `Ingress` (or Istio's own `Gateway`/`VirtualService` custom resources
— see CRDs below) is the layer above that: it maps external hostnames/paths to
a Service, and is what a reverse proxy watches to auto-configure routing —
directly analogous to the Docker-label-based routing auto-homelab already uses
(`traefik.http.routers.<svc>.rule=Host(...)`), just read from the Kubernetes
API instead of the Docker socket.

📘 **Service mesh, sidecar injection:** Istio is a *service mesh* — instead of
just handling external traffic, it injects an Envoy proxy container into
every Pod (a "sidecar," running alongside the app container, sharing its
network namespace). All traffic in and out of the Pod flows through that
sidecar, which is what lets Istio provide mTLS, retries, and traffic
visibility *between your own services* (east-west traffic), not just at the
ingress edge. This is a deliberate, heavier choice than "just use Istio for
ingress" — full learning value, at the cost of an extra Envoy container (and
its CPU/memory) per Pod, and one more moving part per Pod to reason about when
debugging.

- Istio's control plane (`istiod`) and its ingress gateway (a standalone Envoy
  Deployment/Pod, installed via Istio's `gateway` Helm chart) both run in
  `homeserver-system`.
- `homeserver-apps` carries the `istio-injection=enabled` namespace label, so
  every service Pod (Immich, Calibre, etc.) automatically gets an Envoy
  sidecar injected alongside its app container(s) — no per-Deployment opt-in
  needed.
- Because this is a single bare-metal node with no cloud load balancer, the
  ingress gateway is bound directly to the host's ports 80/443 (via
  `hostPort` or `hostNetwork`) rather than through a `LoadBalancer`-type
  Service (which needs something like MetalLB to hand out an external IP —
  unnecessary complexity for one box with one IP).
- Each service gets its own `Gateway` (binds the hostname/port/TLS) plus a
  `VirtualService` (routes that hostname to the backend `Service`) under
  `*.homeserver.example.com`.

📘 **mTLS, PeerAuthentication:** With sidecars injected, Istio can automatically
encrypt and authenticate pod-to-pod traffic using mutual TLS, without the app
code knowing anything about it — each sidecar handles the handshake and
certificate rotation transparently. A cluster-wide `PeerAuthentication` object
in `STRICT` mode (in `istio-system`/`homeserver-system`) requires mTLS for all
meshed traffic; `PERMISSIVE` mode (the default) accepts both, useful while
rolling out. Given this is a single-user homelab, `STRICT` mode is mostly a
learning exercise rather than a real threat-model requirement — but it's the
same pattern used at real multi-service/multi-team scale, which is the point
of practicing it here.

- Set `PeerAuthentication` to `STRICT` once all of `homeserver-apps`'
  services are running with sidecars, so all inter-service calls (e.g. Immich
  → its Postgres/Redis) are mTLS-encrypted automatically.
- `DestinationRule` objects can layer on top for per-service traffic policy
  (load-balancing algorithm, connection pool limits, outlier detection/circuit
  breaking) — not needed on day one, but available without adding anything
  beyond what's already installed.

📘 **CRD (Custom Resource Definition):** Kubernetes lets tools extend its API
with their own object types. Istio ships `Gateway`, `VirtualService`,
`DestinationRule`, and `PeerAuthentication` as CRDs; cert-manager (below)
ships `Certificate`, `Issuer`, and `ClusterIssuer`. Once installed, `kubectl`
treats them like any built-in object.

### DNS model

You clarified: `*.homeserver.example.com` (e.g. `immich.homeserver.example.com`)
must resolve **only inside the home network**, to `192.168.1.250`. Other
subdomains directly off `example.com` (e.g. `blog.example.com`) are
public, real internet services.

That means two independent DNS stories:

- **Internal** (`*.homeserver.example.com`): split-horizon DNS — a resolver
  on your home network (Pi-hole, or your router if it supports local DNS
  overrides/conditional forwarding) answers that wildcard with
  `192.168.1.250`, and this record **never** goes into Cloudflare's public
  zone. Every device on your LAN needs to use that resolver (typically set via
  DHCP on the router). This gives friendly local hostnames without leaking
  your internal IP publicly and without needing a public cert for anything
  internal-only... except we do still want valid HTTPS internally (see TLS
  below), so cert-manager issues a real cert for the wildcard via DNS-01 even
  though the *A record* itself is never public.
- **Public** (e.g. `blog.example.com`): a normal Cloudflare A/CNAME record
  pointing at your home's public IP, with port 80/443 forwarded from your
  router to 192.168.1.250, where the same Istio ingress gateway terminates it. (Or,
  if you'd rather not open inbound ports on your home network at all, a
  Cloudflare Tunnel is the alternative — no port forwarding, outbound-only
  connection from a small agent pod to Cloudflare's edge.)

> ❓ **Open question:** Do you already run a local DNS resolver (Pi-hole,
> AdGuard Home like the old project, or router-native), or does one need to be
> stood up as part of this project? And for public services: are you OK
> forwarding ports 80/443 on your router, or would you prefer a Cloudflare
> Tunnel (no open inbound ports, but one more moving part)?

## 3. TLS

📘 **cert-manager, DNS-01 challenge:** cert-manager is the standard Kubernetes
way to automate issuing/renewing TLS certificates (usually via Let's Encrypt).
A DNS-01 challenge proves you own a domain by creating a temporary TXT record
via a DNS provider's API — Cloudflare's API supports this, which is why it
works even for the internal-only wildcard hostname (no need for that hostname
to be reachable from the internet at all; only the DNS *API* needs to be
reachable, which it always is).

- cert-manager installed in `homeserver-system`, configured with a
  `ClusterIssuer` using the Cloudflare API token (pulled from Vault — see
  Secrets below) for DNS-01.
- One wildcard `Certificate` for `*.homeserver.example.com` (internal), and
  individual or wildcard certificates for whatever public subdomains exist
  under `example.com`.
- Resulting certs land as Kubernetes `Secret` objects that each service's
  `Gateway` references directly by name (`tls.credentialName`) — Istio's
  ingress gateway reads the `Secret` straight from the cluster, no separate
  TLS-store object needed.

## 4. Secrets — phased approach

Running Vault well (unseal handling, raft backup/restore, key rotation) is
close to its own side-project, and it's the one component whose failure mode
is "nothing else can start" (every service depends on it for credentials). To
avoid making the newest, least-proven-by-you piece a day-one dependency, we're
splitting this into two phases:

- **Phase 1 (build this first):** plain Kubernetes `Secret` objects, generated
  and applied by the CLI. Get the cluster, Istio's ingress gateway,
  cert-manager, and the first real services running end-to-end against this
  simpler mechanism.
- **Phase 2 (later, once the baseline above is comfortable):** introduce Vault
  in-cluster and migrate secrets over, without changing how services *consume*
  secrets (both phases end in an ordinary `Secret` object mounted into a Pod —
  see below).

### Phase 1 — plain Kubernetes Secrets

📘 **Secret:** a Kubernetes object holding key/value data (base64-encoded, not
encrypted, by default) that a Pod can consume as environment variables or
mounted files. It's the built-in primitive both Vault-via-ESO and this
simpler phase ultimately produce — which is *why* Phase 2 later is a swap of
how the `Secret` gets created, not a change to any service manifest.

The core requirement carried over from auto-homelab: **secrets are generated,
never hand-picked, and never committed to git.** auto-homelab solved this with
its `configure` command and a pluggable strategy registry (`CONSTANT` /
`GENERATED` random values / `IP` / `STRING` / `PATH`) writing into a
git-ignored `.env`. The direct equivalent here:

- `homeserverctl secrets generate` reuses the same strategy-registry idea, but
  the output is a set of Kubernetes `Secret` manifests (or direct
  `client-go` `Secret` creation) instead of a `.env` file — `GENERATED` values
  use Go's `crypto/rand`, exactly like today.
- A **local, git-ignored copy** of the generated values is still kept on disk
  (mirroring `.env`'s role) purely as a human-readable backup/reference —
  e.g. `secrets/<env>.local.yaml`, covered by `.gitignore` from the very first
  commit of this repo, the same way `.env` is git-ignored in auto-homelab
  today.
- Nothing sensitive ever gets templated into a committed manifest — committed
  manifests only ever reference a `Secret` *by name* (`secretKeyRef`), never
  contain values.
- Rotation/regeneration reuses the same command; re-running it for a
  `GENERATED` field produces a new random value and re-applies the `Secret`.

> ❓ **Open question:** Do you want the local backup copy of generated secrets
> (`secrets/<env>.local.yaml`-equivalent) to also be included in your restic
> backup set from day one, or deliberately left out of backups (since it's
> reference-only and every value is technically re-derivable from the live
> `Secret` objects in the cluster)?

### Phase 2 — migrating to Vault

Once the system above is stable and you're comfortable with the day-to-day
cluster operations, Vault gets introduced as described below. This phase is
deferred, not designed away — the CLI's `secrets` command tree (DESIGN.md) is
shaped so that swapping the backend later doesn't change any service manifest
or how a Pod consumes a secret.

📘 **What Vault adds over plain Secrets:** encryption at rest for the actual
secret store (plain `Secret`s are only base64-encoded, not encrypted, unless
you separately enable encryption-at-rest on the cluster), an audit log of who
read what, and the ability to issue short-lived dynamic credentials (e.g. a
fresh Postgres password per request) instead of one static password forever.

📘 **Seal/unseal:** Vault's storage is encrypted with a master key that is
never stored anywhere on disk in one piece — it's split into key *shares*
(Shamir's Secret Sharing). Whenever Vault starts (including after any restart
of its Pod or the node), it starts *sealed* — unable to decrypt anything —
until enough key shares are supplied to reconstitute the master key. Cloud
Vault deployments usually configure "auto-unseal" against a cloud KMS; a
single homelab box has no such external KMS available, so:

> ❓ **Open question (for when we get here):** How do you want to handle
> unsealing after a reboot? Options: (a) manual — you're physically at this
> box anyway (it's your desktop), so typing 2–3 unseal key shares after a
> restart is a small hands-on step you're already positioned for; (b) store
> the unseal keys encrypted in Bitwarden (you already have it) as a fallback
> location; (c) something fancier (e.g. a `transit` auto-unseal from a second
> tiny Vault instance) — likely overkill for one box. My default
> recommendation is (a) + (b) as a backup copy, not a replacement.

- Deployment: Vault as a single-replica `StatefulSet` in `homeserver-system`,
  using its Integrated Storage backend (`raft`) — no separate database needed,
  Vault manages its own replicated log on a `PersistentVolumeClaim` (see
  Storage below).
- Backing up Vault: raft supports online snapshots (`vault operator raft
  snapshot save`). A CronJob takes a periodic snapshot and feeds it into the
  same restic/B2 backup pipeline as everything else (see Backups below) — so
  Vault's data is recoverable the same way as any other service's.
- Getting secrets *into* pods: two standard patterns exist —
  1. **Vault Agent Injector** — a sidecar container injected into each Pod
     that fetches secrets from Vault and writes them to a shared in-memory
     file, refreshed automatically.
  2. **External Secrets Operator (ESO)** — a controller that reads from Vault
     and materializes ordinary Kubernetes `Secret` objects, refreshed on an
     interval.

  Recommendation: **ESO**, precisely because it keeps producing plain
  `Secret` objects — the same end state Phase 1 already produces, which is
  what makes this migration additive rather than disruptive. The Go CLI's
  `secrets` command switches from writing `Secret`s directly to writing into
  Vault; ESO takes over turning those into `Secret`s from there.

## 5. Storage

📘 **PersistentVolume (PV), PersistentVolumeClaim (PVC), StorageClass:** Pods
are ephemeral and by default have no persistent disk. A PVC is a request for
storage ("give me 20Gi"); a PV is the actual piece of storage that satisfies
it; a `StorageClass` is what lets PVs be created automatically on demand
instead of by hand.

- `local-path-provisioner` (Rancher's lightweight dynamic provisioner) as the
  default `StorageClass` — it carves PVs directly out of the node's local
  disk. This is the natural single-node equivalent of the bind-mounted host
  directories the Compose setup uses today (e.g. Immich's `UPLOAD_LOCATION`).
- Every service that currently has a bind mount gets a PVC instead — same
  data, addressed the Kubernetes-native way.

> everything live on the same disk the OS is on for now?

## 6. Backups

The old project's design work here (`documentation/kubernetes-migration/07-backup.md`)
already solved this well — we're adopting it directly:

📘 **CronJob, initContainer:** A `CronJob` runs a `Job` (a Pod that runs to
completion, unlike a long-lived Deployment) on a schedule — the Kubernetes
equivalent of a cron entry, but one that runs *inside* the cluster and can
mount the same volumes as the service it's backing up. An `initContainer` runs
to completion *before* a Pod's main containers start — useful for one-off setup
steps like taking a database dump before the backup step copies it out.

- One `CronJob` per stateful service, each: takes a DB dump via a short-lived
  Job/initContainer if the service has a database (Postgres, MariaDB), then
  runs `restic backup` directly against the same PVC restic backs up — no
  more local staging copy, which removes the "2x disk space" problem the
  current Compose-based two-phase (`backup local` → `backup cloud`) design
  has.
- restic's B2 credentials and repository password come from Vault via the
  same ESO-synced `Secret` mechanism as any other service.
- Retention policy: keep the current simple `--keep-within <N>d --prune`
  scheme initially; upgrading to a daily/weekly/monthly GFS-style scheme is a
  clean future improvement (already flagged in the old project's own
  `IMPROVEMENTS.md`), not a blocker for v1.
- Vault's own raft snapshots feed into this same pipeline, so a full disaster
  recovery restores both application data and the secrets store.
- Restore is CLI-driven (see DESIGN.md) rather than the current ad hoc shell
  scripts, but follows the same logical steps: scale the service down, wipe/
  restore its PVC content from a restic snapshot, restore the DB dump into a
  freshly started DB, scale back up.

## 7. Services

📘 **Deployment vs. StatefulSet:** A `Deployment` manages stateless,
interchangeable Pods (any replica can be replaced by an identical new one). A
`StatefulSet` is for things with identity/state that shouldn't be casually
replaced or run as multiple interchangeable copies — databases, primarily —
and gives each replica a stable name and its own dedicated PVC.

Immich is the flagship/most complex service (per your note: DB + file storage
+ ML container), so it's the reference example other services will follow the
same pattern as:

| Component | Kind | Notes |
|---|---|---|
| `immich-server` | Deployment | main app |
| `immich-machine-learning` | Deployment | ML inference, no ingress needed |
| `immich-redis` | Deployment | cache, no persistence needed |
| `immich-db` | StatefulSet | Postgres w/ pgvector, PVC-backed |
| — | PVC | photo/video upload library |
| — | Service ×N | one per component needing internal DNS |
| — | Gateway + VirtualService | `immich.homeserver.example.com` → `immich-server` |
| — | CronJob | pg_dump + restic backup of DB + upload PVC |

Every other service (Calibre, Paperless, Firefly, Navidrome, …) is a simpler
version of this same shape (Deployment/StatefulSet + PVC + Service +
Gateway/VirtualService + optional backup CronJob).

## 8. Local development (macOS)

- A local Kubernetes cluster via **kind** (Kubernetes-in-Docker). Recommended
  over k3d/minikube because it runs the most "vanilla" upstream Kubernetes —
  closest behavior to the real kubeadm cluster, no bundled ingress/LB
  replacing the ones we're deliberately choosing ourselves (Istio, etc.).
  kind supports `extraPortMappings` to expose 80/443 from the Mac's Docker
  Desktop straight into the cluster, mirroring how the Istio ingress gateway
  binds to the host on the Debian box.
- Same manifests, same Go CLI commands — only the cluster context and the
  Vault instance/credentials differ (a throwaway dev Vault, possibly Vault's
  built-in `-dev` mode, seeded with fake API tokens for Cloudflare/B2 so
  nothing touches real infrastructure).
- The CLI resolves "which environment am I targeting" the same way it resolves
  which value overlay to apply (see DESIGN.md's config-layering section) —
  you invoke the exact same commands on both machines.
